Open redirect + javascript:-URI XSS via an unvalidated query param in Deriv's redirect flow

Deriv.com (Traders Hub) · web · HIGH 7.x · reported to HackerOne
open-source review + live browser capture + local DOM-verified reproduction · reported Nov 2026

tldr

The Traders Hub trusts its ext_platform_url query parameter end-to-end: no origin check, no protocol allowlist, anywhere in the chain. The value is decoded and stored verbatim into client state, then handed straight to window.location.replace() when the user confirms or cancels the real-account-signup currency modal. A crafted link navigates a logged-in trader to an arbitrary attacker host — and a javascript: pseudo-URL reaches the same sink unfiltered, executing script in the victim's session origin.

the bug

  • Ingestion, no validation: the parameter enters via decodeURI() and is stored RAW through the external-params setter — a repo-wide search finds zero allowlist or protocol checks on it.
  • The sink: the legacy-platform redirect helper passes the stored raw value straight to window.location.replace(url). Per the HTML spec, a javascript: URL navigated via Location.replace() executes as script.
  • Fires on normal interaction: the sink call sits on BOTH handlers of the add-currency dialog — Confirm and Cancel — plus the signup container. No exotic clicks required.
  • Survives official redirects: the attacker value rides intact through the product's own 302 hop chain (hub → marketing domain → regional hub). The lure looks completely legitimate — the victim watches official Deriv redirects carry the poisoned destination.
  • Bonus planting: the same flow stores attacker-controlled email and code URL parameters into persistent LocalStore-backed stores, which the update-email modal consumes and auto-submits via the change-email API under the victim's session.

methodology

Found by reviewing the public client source and tracing where a query parameter enters client state and which navigation sinks consume it. The redirect survival was observed in a live browser; the sink behavior was confirmed in an isolated local reproduction — deliberately without touching any production account, and without dropping any working exploit payload publicly.

Honesty about what was and wasn't tested is part of the report's credibility: separating live observation from local reproduction from origin-level claims is the discipline.

impact

  • Post-authentication phishing pivot: the victim lands on an attacker host right after clicking Confirm/Cancel inside their trading session — following a chain of official redirects, so the lure is maximally convincing.
  • javascript: execution in session origin: script runs with full DOM access to the hub — fabricated balance/withdrawal UI, captured interactions, session-visible data. An XSS-class primitive, not merely navigation.
  • Persistent session steering: the stored value survives the history cleanup and is re-propagated across internal hops — one crafted link keeps steering the session.
  • Chainable to account-flow confusion: attacker-planted email/code values persisted to storage and auto-submitted by the update-email modal chain naturally into a full phishing-driven account-takeover pretext.
