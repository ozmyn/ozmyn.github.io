One-click forced logout: deep link → WebView JS bridge in inDrive (Android)

inDrive · Android · MED 6.3 · reported to HackerOne
static APK analysis + live testing · reported Nov 2026

tldr

inDrive's Android app ships an exported Activity (WebDialogActivity) reachable via the indrive://webdialog?url=... deep link. It takes the url parameter and loads it straight into an in-app WebView — no domain allowlist — with a JavaScript bridge attached unconditionally. Any attacker link (browser, WhatsApp, SMS) opens attacker-controlled content inside the real app, under legitimate inDrive branding, with bridge access.

the bug

  • The Activity is exported="true" with a BROWSABLE/VIEW intent-filter for the indrive:// scheme.
  • Its handler passes the deep link's url query parameter through Uri.decode and loads it into the WebView — the http/https and domain checks only exist on a different code branch.
  • The JS bridge (addJavascriptInterface) is attached unconditionally, and the page's postMessage dispatcher enforces no per-action host check.
  • The key miss: an older, deprecated Activity had a referrer-package check that rejected browser launches — the current one shipped without it. Incomplete security migration.

impact — confirmed live on my own device & account

  • logout_with_message — the headline: forced logout + attacker-controlled message rendered inside the authentic app. A high-conviction phishing primitive: "your account was blocked → re-enter your credentials here", with none of the usual external-browser signals.
  • copyToClipboard — silent clipboard write (crypto-address swap) without confirmation.
  • openShareMenu — native share sheet pre-filled with attacker text.
  • openCamera — reaches the real KYC capture flow.

The base vector is one-click (a tap on the link). On a Xiaomi/HyperOS device I verified an auto-trigger variant firing the deep link zero-click — interaction requirements are device-dependent, which is why the severity lands Medium 6.3, up to 7.3 High where zero-click applies.
