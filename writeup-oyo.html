Exported ContentProvider + a hardcoded AES key: staff token theft in OYO OS (Android)

OYO OS (com.oyo.property) · Android · HIGH 7.x · reported to HackerOne
APK static analysis + JNI harness + crypto roundtrip · reported Nov 2026

tldr

OYO's property-management Android app stores the logged-in staff member's full credential set — user ID, email, phone number, name, role, and the live session access token — inside an SQLite-backed ContentProvider that is declared android:exported="true" with no permission attribute and no runtime permission check. The only thing standing between that blob and the world is AES encryption under a key hardcoded into the APK's native library. Anyone holding the public APK — which is everyone — can extract it.

Net result: any unprivileged application installed on a staff device (or an adb session on a connected device) silently recovers a property manager's session token and PII.

the bug

  • The provider is exported="true" with no android:permission / readPermission / writePermission, and the provider class performs no permission check in query() / update() / delete().
  • The write path packs USER_ID, phone number, country code, email, first/last name, role and the live ACCESS_TOKEN into a single AES-encrypted column — one row, everything an attacker wants.
  • The cipher is AES/ECB (Cipher.getInstance("AES"), no IV, deterministic) — and the key comes from NativeBridge.getAutoLoginKey(), embedded as rodata in libapi-key.so shipped in all four ABI builds.
  • The companion OYO Partner app declares a <queries> entry for this exact provider — confirming it is live cross-app SSO transport, not dead code.

the proof

The interesting part: I didn't guess the key from strings — I executed the shipped native library. A minimal JNI harness dlopens the patched ELF and calls the same entry points the app does:

gcc -o jniharness jniharness.c -ldl LD_LIBRARY_PATH=. ./jniharness libapi-key-patched.so # output (masked) API_KEY=[s6po********:pNcM********] AUTO_LOGIN_KEY=[V02o******...****Yv+E4=] # base64 → 32-byte AES-256 key

Then an offline encrypt → decrypt roundtrip mirroring the app's own crypto class — same cipher transformation, same padding — succeeded bit-exactly: all 10 credential fields recovered from the blob format, using researcher-controlled dummy data only.

Secrecy-by-unreachability fails the moment the artifact it depends on is public. A key inside a distributable APK is not a secret — it's an obfuscation with extra steps.

impact

  • Plaintext PII: email, phone number + country code, first/last name, user ID.
  • The live session ACCESS_TOKEN and role for the property-management backend.
  • The app's own request interceptor reconstructs the auth-header formula — a recovered token is directly replayable against the HMS API: bookings, revenue data, pricing controls, guest data.
  • Because ECB is deterministic and the key is public, the same credentials recover from any backup or data snapshot — the exposure scales across the entire partner fleet using the app.

outcome & lessons

  • Reported to OYO via HackerOne; closed as a duplicate of an earlier report for the same component — the class was real and already known to the program. Triaged High (7 ~ 8.9).
  • Lesson 1: exported components are the Android equivalent of unauthenticated endpoints. Enumerate every provider/receiver/activity before touching anything else.
  • Lesson 2: test crypto assumptions by executing the shipped binary, not by eyeballing it. A JNI harness turns "probably extractable" into a proven key.
  • Lesson 3: cross-app <queries> declarations in sibling apps are a free map of which internal transports are actually live.
  • Lesson 4: duplicate ≠ wasted. Triaged severity on the same class still proves the finding quality — and the methodology transfers to every other app in the fleet.
